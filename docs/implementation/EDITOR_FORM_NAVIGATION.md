# Editor Form Navigation and Sticky Preview

Date: July 27, 2026
Status: Implemented on `resume.html` and `docs.html`; the sticky preview applies to all four editors

## The Problem

The resume form is five fieldsets, fourteen base fields, plus repeating experience and education entries — roughly twenty-eight inputs once a visitor has entered two jobs and two qualifications. `docs.html` is larger still. Reaching the later sections meant scrolling a long way.

Scroll length was the visible symptom. The actual defect was underneath it: both panes were ordinary page children, so the preview scrolled away with the form. By the time a visitor reached Education, the document sheet had left the screen entirely. The live preview — the reason the split view exists, and the product's main differentiator — was switched off exactly when the form became long enough to need it.

## Why Not Tabs

The prompting example was a resume builder that segments its form into eight tabs (Personal, Summary, Experience, Education, Skills, Projects, Languages, Interests). That is a common and legitimate pattern, but it was rejected here for three reasons.

**It hides fields.** A visitor who never notices the Skills tab exports a resume with no skills. Making that safe requires per-tab completion indicators, which is more machinery than five sections justify.

**It breaks the browser's own search.** Ctrl+F across the form stops working, and there is no way to review everything entered in a single pass before exporting.

**It collides with an existing control.** Below 48rem the editors already use a tab row to switch between Edit Form and Live Preview. A second tab row directly beneath it, controlling something different, is genuinely confusing.

Tabs also solve only the symptom. The preview would still be absent while the visitor typed.

## What Was Built

### Sticky preview pane

Above 48rem the preview pane is `position: sticky` with `align-self: start`, so it holds its place while the form scrolls beside it. Every keystroke visibly lands on the document however far down the form the visitor has gone.

`align-self: start` is the load-bearing part. The grid row track is as tall as the taller pane (the form), which gives the preview's grid area room for the sticky element to travel. Without it the pane would stretch to fill the track and have nowhere to move.

The pane is capped at `calc(100vh - 7rem)` with `overflow-y: auto`, so a long document scrolls inside the pane rather than running past the viewport. A side effect worth knowing: this makes the pane a scroll container, so the sticky export bar inside it now sticks to the bottom of the pane rather than to the page. That is the better behaviour and needed no extra rule.

Below 48rem nothing changes — the existing Edit/Preview tabs already solve it there, and a sticky pane on a phone would fight the mobile ad anchor.

### Section jump list

`initFormNav()` in `site/js/app.js` builds a sticky row of anchors at the top of the form pane, one per fieldset, labelled from each fieldset's own `<legend>`. Clicking one scrolls to that section and focuses its first field. An `IntersectionObserver` marks whichever section is currently in view, which is what gives it the same sense of place a tab row provides.

Design points worth preserving:

- **Built from the DOM, not from a list.** The nav is generated by reading the form's fieldsets, so adding a fieldset adds a nav entry automatically. There is no second place to update and the two cannot drift.
- **Hidden fieldsets are skipped.** `docs.html` hides the fieldsets that do not belong to the selected document type, and a nav listing them would jump to nothing. Visibility is tested with `offsetParent`, which is null for a hidden element.
- **Rebuilt on document-type change only.** `applyDocType()` runs on every keystroke through `persistAndRender`, so `docs.js` guards the rebuild on the type actually changing. The previous `IntersectionObserver` is disconnected on each rebuild.
- **Fewer than two visible sections renders nothing.** The row hides itself rather than showing a single pointless link.
- **The click handler calls `preventDefault()`** and scrolls manually, so the section lands below the sticky header rather than behind it, and the URL is not littered with fragments the visitor did not choose.

`scroll-margin-top: 9rem` on `.editor-pane fieldset` clears the sticky site header plus the nav row itself when a section is jumped to.

## Print

Three of these rules had to be undone for print, and one of them mattered:

```css
.preview-pane {
    position: static !important;
    max-height: none !important;
    overflow: visible !important;
}
```

Without the height and overflow resets the printed sheet would be **clipped at one viewport height** and the remainder would never reach the paper. The nav row is hidden in print alongside the other editor furniture.

## Not Applied To

`poster.html` and `mockup.html` get the sticky preview but no jump list: their control panels are short enough that a navigation row would be more chrome than help. The mount point is a single element and the logic is already generic, so either can adopt it later by adding `<nav class="form-nav" data-form-nav hidden>` inside the editor pane.

## Verification

22-case harness over `initFormNav()`: build from legends, id slugification including unslugifiable labels, hidden-fieldset skipping, rebuild replacing rather than duplicating and disconnecting the previous observer, the single-section suppression, click behaviour (default prevented, section scrolled, first field focused), highlight tracking as sections enter and leave view, and a page with no mount booting without error.

Also re-run green: the 32-case editor-ad band harness, the 30-case `js/app.js` regression harness, and the structural pass over all 24 pages.

**Not verified:** the sticky preview against a real browser's scroll behaviour, and print output. Both need a device pass. The print rules are written but were checked as CSS only, not as a rendered print job — the same gap already recorded for the document builder.
