## 1. Structure review and first defects

Asked whether the flat repository layout was correct and why footer links did not appear on the guides page.

Findings and resolutions:

- **Flat pages are correct and stay flat.** With a static host the directory layout is the URL layout, so nesting pages under `pages/` would rename every public URL for tidiness alone. Rejected.
- **Internal files were publicly served.** `publish = "."` meant `docs/**` (including the operational handoff document with ad zone keys and analytics IDs), `PRD.md`, `CLAUDE.md`, `README.md` and `.github/` all answered 200 and were crawlable. First closed with forced 404 rules, superseded the same day by item 2. No credentials were exposed: the zone keys and Clarity ID are in every page's source by nature.
- **Footer links and the guides page are unconnected by construction.** The footer is hand-written; `blog.html` renders only from `js/blog-data.js`. Not a defect, but it surfaced the crawlability gap in item 3.
- **Exported post pages shipped a stale footer** (single row, no landing-page columns, no social icons) because the generator's shell in `js/admin.js` was never updated alongside the hand-maintained pages. Extracted a single `FOOTER` constant.
- **Homepage guide cards never rendered an excerpt.** `js/app.js` read `post.standfirst`; the field is `description`. A truthiness check on a missing property, silent since it was written.

## 3. Crawlability: blog posts had no static inbound link

Every link to a post was created in JavaScript (`initBlogIndex()` and `initGuidesStrip()`), so `sitemap.xml` was the only static route to `blog/<slug>.html`. Same defect class as the button-to-anchor fix of July 26.

- `blog.html` now carries a visible `<nav class="guide-archive">` listing every published post, outside the containers the renderer clears so it cannot be duplicated or removed.
- Generated by a new **Copy Guides Archive** export in `admin.html`, so it cannot disagree with the data file or the exported pages. Publishing a post is now four artifacts.
- The homepage guides strip stays a JavaScript render deliberately: it is a "latest three" widget, and `blog.html` is statically linked from the nav and footer of all 22 pages, so the crawl path no longer depends on it.

Its links deliberately omit `data-target` so error recovery does not route through the ad interstitial.

## 5. "Index page is blank"

Reported with a screenshot showing a file listing instead of the homepage. `site/index.html` was verified intact (15 cards, 5,638 characters of text). Two faults, only one caused by the migration:

- **`{"cleanUrls": false}` also disables serve's directory-index resolution.** The config added on July 20 to stop query strings being dropped meant `GET /` never resolved to `index.html`. Present since July 20; invisible until the move changed what the listing showed. Proven by isolating the file with and without it.
- **The server was rooted at the repository.** `serve` returns `site/index.html` for the URL `/site` without redirecting to `/site/`, so relative assets resolved one level too high and 404'd.

Fixed with one `serve.json` at the repository root: `public: "site"`, `cleanUrls: false`, `directoryListing: false`, and a `/` to `/index.html` rewrite. `site/serve.json` deleted, so the publish directory now holds only deployables and `netlify.toml` carries no internal-file rules at all. `.vscode/settings.json` added to root Live Server at `/site`, since it would hit the same fault.

## 6. Article pages served zero ads

Raised as "why not add ads on the guides/articles." They were already designed, zoned and live — five zones, all with keys — but the static post pages carried no ad hosts and did not load `js/blog.js`, so four zones were inert on the pages readers reach. `post.html`, which did have them, had been 301'd away on July 26. Collateral damage from that migration; it failed silently because empty ad hosts render nothing.

- Hosts now emitted in the generated markup: leaderboard, in-content 300x250, end-of-article 300x250, and a 160x600 rail in a `.post-layout` wrapper.
- `adBreakIndex()` extracted so the runtime and generated paths agree, and fixed: the old rule could drop the ad between a heading and the paragraph it introduces. It now slides past headings and lands between sections.
- `:empty` collapse rules added for all ad hosts, which matters now that hosts ship in static markup and exist even when unfilled.
- Body serialization made reproducible: the generator emitted one unbroken line while the committed page had been pretty-printed by hand, so a re-export could never match the repository.

## 7. Landing page ads and the shared placement module

Asked why the template landing pages had no ads given the visible empty space in the hero.

- **That space is a grid artifact, not a slot.** The 4:5 preview column is always taller than the headline and CTA beside it; `align-items: start` piled the difference under the button. Changed to `center`.
- **The hero is the wrong placement regardless.** These pages exist to send clicks into `loading.html`, where a Popunder, two 300x250s and the Social Bar run across a ten-second dwell — worth far more than one banner impression from a visitor about to leave.
- **One 300x250 per landing page**, between the body copy and the FAQ: above both the closing CTA band and related templates, so neither conversion element is competed with. Passive format only; Popunder and Social Bar stay off every indexable page.
- **`js/ads.js` extracted** (187 lines, no dependencies) as the single placement registry, since landing pages were the third page family to need one and the table lived inside a 790-line content library. `js/blog.js` dropped to 655 lines. Auto-mounting is opt-in through `data-ads-static`, which is what prevents a renderer-driven page double-counting impressions. Side effect: generated post pages stopped loading `js/blog.js` and `js/blog-data.js`, neither of which they read, and the post database grows with every published post.
