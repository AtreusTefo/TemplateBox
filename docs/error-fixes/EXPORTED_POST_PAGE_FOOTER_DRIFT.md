# Blog Post Pages Ship an Outdated Footer: No Landing-Page Links, No Social Row

Date: July 27, 2026
Updated: July 27, 2026 — the footer was restructured into five columns later the same day, and two further drift cases were found and normalized (see Second Pass below). The `FOOTER` constant described here is still the single source for generated pages.
Status: Fixed

## Issue Title

Reported as "why aren't the guides in the footer on the guides page." On a blog post page the footer looks nothing like the footer on every other page: instead of the four link columns (Receipts and Invoices, Creative Tools, Learn, Company) plus the social icon row, it shows a single row of five plain links and the tagline. All nine document landing pages and all four social profiles are missing from that footer.

## Root Cause

The footer is hand-copied HTML, duplicated across all 21 root pages. Blog post pages are the one exception: they are generated by the **Download Post Pages** action in `admin.html`, which builds each page from a string template in `buildPostPage()` in `js/admin.js`.

That template carried the footer as it existed when the blog system was built (July 18, 2026) — a single `.footer-base` block containing `.footer-links`. The site footer was later rebuilt into the four-column `.footer-cols` layout, and the social row was added on July 25, 2026. Both changes were applied to the hand-maintained pages and neither reached the generator, so every exported post page reproduced the old footer.

The consequence is not only cosmetic. Post pages are indexable content and were passing no internal link equity to the nine landing pages that the footer exists to support, and the guides surface was the one place on the site where the footer's own content links disappeared.

Note the shape of this defect: it is drift between two copies of markup with no shared source. It will recur on the next footer change unless the generator is updated at the same time.

## Fix Applied

- `js/admin.js`: extracted the footer into a single `FOOTER` constant defined next to `POST_ORIGIN`, holding the current four-column footer plus the social row, with every path prefixed `../` because post pages live one level down in `blog/`. `buildPostPage()` now interpolates `FOOTER` where the inline footer string used to be. The constant carries a comment stating that the footer is hand-copied project-wide and must be updated here whenever the root pages change.
- `blog/free-cv-resume-templates-build-professional-resume-fast.html`: the one already-exported post page was updated to the new footer, byte-for-byte matching what the generator now emits (rather than re-exporting through the browser).

## Testing Steps

1. Verify the three copies agree. At fix time this was done with a throwaway Node script (not committed) that extracts the `FOOTER` constant from `js/admin.js` with a regex, `eval`s it, slices the `.site-footer` block out of each HTML file, and asserts:
   - generator output is byte-identical to the exported post page's footer — passed
   - generator output equals `index.html`'s footer once `href="../` is normalized to `href="` — passed
   - every relative `href` in the exported footer resolves to a file on disk — 16 links checked, none missing
2. `node --check js/admin.js` — the template is one long string concatenation, so a quoting mistake is a syntax error.
3. Structural check of the exported page: tag balance clean, exactly one `<h1>`, no duplicate `id` attributes. Confirmed at fix time with a lenient `html.parser` pass.
4. Open `blog/<slug>.html` locally and confirm the footer renders as four columns with the social icons, that each footer link resolves (the `../` prefixes are what make this work from inside `blog/`), and that nothing overflows horizontally at 320px.
5. Re-export from `admin.html` (Download Post Pages) and diff the output against the committed file. They must be identical.

## Second Pass (July 27, 2026): restructure, and two more drifted copies

Auditing every page's footer to apply the restructure turned up two cases the first pass had not looked for, because the first pass compared footer *content* after stripping leading whitespace and only against `index.html`:

- **`privacy.html` had an accordion footer.** It alone wrapped each column in `<details open><summary><h2>...</h2></summary>`. No rule anywhere in `css/style.css` styles `details` inside a footer, so it rendered with the browser's default disclosure triangles — visibly different from the other 20 pages. Normalized to the canonical markup.
- **The nine landing pages indented the opening tag differently.** `<footer class="site-footer">` sat at column 0 on those pages and at four spaces everywhere else, a leftover from their one-time generation. The inner lines matched, which is why a content-only comparison reported all copies identical. Normalized.

The restructure itself: the old "Creative Tools" column mixed three landing pages with two of the four editors, leaving `docs.html` and `poster.html` looking arbitrarily excluded. There are now five columns — Receipts and Invoices, Resumes and Creative, Editors, Learn, Company — with landing pages and editors separated and each group complete. `.footer-cols` uses `repeat(auto-fit, minmax(11rem, 1fr))`, so no CSS change was needed.

Application method, which is the part worth repeating next time: a single script held the column and social definitions, generated the block once, wrote it into all 22 pages (adding `../` for the pages under `blog/`), and re-quoted the same string as the `FOOTER` constant in `js/admin.js`. Hand-editing 22 copies is what produced every case in this document. Verified afterwards: all 22 copies hash identically after normalizing the `../` prefix, the generator output is byte-identical to the exported post page, and all 18 relative link targets resolve. `site/404.html`, added in the same pass, took the same footer and is included in that count.

## Troubleshooting

- If a re-exported page differs from the committed one, the hand-edit and the generator have diverged again — treat `js/admin.js` as authoritative and re-export rather than hand-patching the HTML.
- If footer links 404 from a post page, check the `../` prefix. Root pages use bare relative paths; anything in `blog/` needs one level up. `index.html#templates` needs it too (`../index.html#templates`).
- The print stylesheet hides `.site-footer`, so this change cannot affect any PDF or print output.
