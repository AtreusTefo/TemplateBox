## What TemplateBox Is

A 100% client-side, serverless template personalization engine at templatebox.win. Four live tools, backed by nine search-intent landing pages, a guides blog, and About/Terms/Privacy pages. The tools: a CV/Resume builder, a Business Document builder (rent receipts, cash payment receipts, itemized business receipts, sales and cash receipt forms, invoices, employee warning notices), a Poster/Canvas creator, and a Product Mockup generator for print-on-demand sellers (t-shirt, hoodie, mug, packaging box). Monetized through a mandatory 10-second ad loading page between the catalog and the editor. Full requirements and design system live in `PRD.md` and `CLAUDE.md`.

## The Monetized Flow (as implemented)

```
index.html card click
  -> ad click shield (inline in index.html <head>, above the Popunder tag):
     only [data-target] launch clicks are allowed to reach the ad script's
     document-level handler; pills, nav and page clicks never do
  -> js/app.js launchTemplate(): navigation to loading.html?target=resume|poster
     deferred 150ms, then re-issued every 700ms until the page unloads, so the
     Popunder's same-click fallback redirect cannot out-race or out-order it
  -> loading.html: 10s countdown, 2 banners + Social Bar render
  -> at 0: navigation watchdog re-issues location.replace(editorUrl) every 700ms
     until the page actually unloads, so ad-initiated navigations can't strand the user
  -> resume.html or poster.html: localStorage-backed editor carrying passive
     banners by viewport band (three 300x250 in a rail at 93rem+, one 160x600
     rail 84-93rem, 728x90 leaderboard 48-84rem, 320x50 anchor below 48rem)
     and no active format. Editors carry no site footer
```

Because of the shield, index.html's own click behaviours (filter pills, the continue-strip discard button) are bound as window-capture delegated listeners in `js/app.js`, not element-level listeners — element listeners below window never fire for shielded clicks. Keep that pattern for anything new added to index.html that is not a launch control. See `docs/error-fixes/POPUNDER_HIJACKS_ALL_PAGE_CLICKS_FIX.md`.

`EDITOR_ROUTES` in `js/app.js` is the whitelist mapping `target` query values to editor pages — this is what makes the redirect immune to open-redirect tampering. `loading.html` carries a second, dependency-free copy of this same whitelist inline (see below) — **both must be updated when adding a new editor**, or the fallback path silently sends unrecognized/failed cases to the default editor instead of the new one.

An editor that serves several catalog cards (docs.html serves six) also needs a **variant hand-off**: `initCatalog()` writes the clicked card's `data-doc` value to `localStorage` under `tb_editor_preset`, and `TB.takePreset()` reads and clears it on arrival. The preset is never a route — the editor matches it against its own variant table, so a tampered value can only resolve to something that already ships. Clearing on read is what stops a later direct visit from re-applying a stale card choice over the visitor's saved work.

## Known Issues Already Solved (see docs/error-fixes/ for full write-ups)

- **R2_CUSTOM_DOMAIN_ON_APEX_TAKES_DOWN_SITE.md** (July 30, 2026) — the entire site returned 404 from Cloudflare, with no Netlify headers, rendering a storage "Object not found / Is this your bucket?" page while `templatebox.netlify.app` served 200. Cause: an R2 bucket (`product-mockups`) had `templatebox.win` — the apex, i.e. the website — bound as its Custom Domain. An R2 custom domain binds the *whole hostname* to the bucket, so nothing reached Netlify, and the bucket was empty. Uploading objects would not have helped: a bucket has no page routing and Cloudflare does not serve bucket listings at a domain root, so `/` 404s by design. **The remedy has a destructive second step:** removing the binding also deletes the DNS record it created, taking the site from 404 to NXDOMAIN, which reads as a worse failure — the apex `CNAME` to `templatebox.netlify.app` must then be recreated by hand, left DNS-only until Netlify verifies it, and only then set to Proxied. `www` also appeared broken throughout despite an intact record, because Netlify 301s it to the primary domain and the apex was what was failing. Resolved the same day; verified with `Server: cloudflare` and `x-nf-request-id` present on the same response.

- **RESUME_PDF_RASTERIZED_TEXT_FIX.md** — html2pdf.js rasterizes text (fails ATS parsing); replaced with jsPDF native `doc.text()` API. Verified with an automated PDF-stream inspection (real `Tj` text operators, no embedded images) plus a manual browser highlight-copy-paste test.
- **ADSTERRA_AD_CONFLICT_FIX.md** — Popunder's fallback redirect could hijack the foreground tab when popups were blocked (last navigation assignment wins); fixed with the 150ms deferred nav in `launchTemplate()`. Also: two banner tags sharing one page context clobbered each other's global `atOptions`; fixed by isolating each in its own `srcdoc` iframe. The deferral half of this fix was superseded July 27 (next entry); the srcdoc isolation stands.
- **POPUNDER_HIJACKS_ALL_PAGE_CLICKS_FIX.md** (July 27, 2026) — the hijack above was never launch-click-specific: the Popunder's document-level handler observes every click on index.html, so popup-blocked visitors were redirected off-site from filter pills (no competing navigation at all), nav links (coin-flip race) and even launch clicks (one-shot 150ms deferral loses to a fast-committing ad). Fixed with an inline window-capture click shield in index.html that starves the ad script of every non-`[data-target]` interaction and refuses injected foreign-origin anchors; pills and the continue-strip discard moved to window-capture delegation to survive the shield; `launchTemplate()` now re-issues its navigation every 700ms until unload (loading.html's watchdog pattern). Verified with a 16-check Playwright run against a simulated hijacking ad handler (attached earlier than the real one can be) with the ad redirect delayed 600ms to mirror a cross-origin round trip. Known cost: Clarity's document-level click capture on index.html is starved too; scroll/movement replay unaffected. Revised July 28, 2026: the shield alone bricked the page against the real ad script, which captures the first click with a transparent full-viewport layer (random id, z-index 2147483650) removed only from inside its own document-level listener -- the very listener the shield starves -- so no click or hover reached the page at all. An overlay neutralizer in the same inline block now forces pointer-events:none on any oversized fixed/absolute element the page does not ship (MutationObserver plus 700ms sweep, geometry-based because the id is random). Verified by reproducing the dead page with a faithful simulation of the decoded layer mechanism, then passing 9 overlay checks and the updated 17-check regression suite.
- **LOADING_REDIRECT_STALL_FIX.md** — same "last navigation wins" defect class, but spanning the whole loading.html page lifetime instead of one click; fixed with the persistent navigation watchdog described above.
- **SOCIAL_BAR_NOT_DISPLAYING.md** — not a defect. Full delivery chain verified (script serves, runtime domains resolve and respond). Non-display was per-visitor frequency capping plus the widget's animated entrance losing the race against the page's 10-second lifetime. Confirmed serving via Adsterra dashboard impression counts.
- **INTERNAL_FILES_PUBLICLY_SERVED.md** — `publish = "."` plus no build step meant the whole workspace was the web root: `docs/**` (including this file, with the Adsterra zone keys and Clarity ID), `PRD.md`, `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `README.md` and `.github/` all answered 200 and were crawlable. First fixed with `force = true` 404 redirect rules, then superseded the same day by moving the deployable site into `site/` and setting `publish = "site"`, so internal files are not in the deploy at all. Treat the previously-served contents as having been public.
- **STATIC_POST_PAGES_SERVED_NO_ADS.md** — the July 26 move to static post pages produced a generator shell with no ad hosts and no `js/blog.js` include, so four live Adsterra zones (leaderboard, in-content 300x250, end-of-article 300x250, 160x600 rail) served nothing on the pages readers actually reach; `post.html`, which did have them, had been 301'd away. Fixed by emitting the hosts in the generated markup and auto-filling them from the shared registry (`initStaticPost()` at first, replaced hours later by the generic `TBAds` auto-mount when the landing pages needed the same thing). Same generator and same class of omission as the footer drift below. Also extracted `adBreakIndex()` (now in `js/ads.js`) so the runtime and generated paths position the in-content break identically, and fixed that rule placing an ad between a heading and its own first paragraph.
- **BLOG_POSTS_NOT_CRAWLABLE_WITHOUT_JAVASCRIPT.md** — every link to a post was created in JavaScript (`initBlogIndex()` in `js/blog.js`, `initGuidesStrip()` in `js/app.js`), so the served markup of `blog.html` contained no post link and `sitemap.xml` was the only static route to `blog/<slug>.html`. Fixed with a visible `<nav class="guide-archive">` list on `blog.html`, generated by a new "Copy Guides Archive" export in `admin.html` so it cannot disagree with the data file or the exported pages. Same defect class as the button-to-anchor and static-post-page fixes of July 26.
- **EXPORTED_POST_PAGE_FOOTER_DRIFT.md** — pages exported by `admin.html` carried the pre-July-25 single-row footer, so post pages linked to none of the nine landing pages and showed no social row. The footer string in `js/admin.js` had not been updated alongside the 21 hand-maintained copies. Now a single `FOOTER` constant in `js/admin.js`; the one existing post page was brought in line and verified byte-identical to the generator output.
- **HOMEPAGE_GUIDE_CARD_MISSING_EXCERPT.md** — `initGuidesStrip()` read `post.standfirst`; the field is `description` (`standfirst` is the CSS class on a post page). Truthiness guard on a missing property, so every homepage guide card silently dropped its excerpt.
- **LOCAL_INDEX_PAGE_BLANK_DIRECTORY_LISTING_INSTEAD_OF_HOMEPAGE.md** — reported as "index page is blank." Not an application defect: `site/index.html` was verified intact. Two faults. (1) `{"cleanUrls": false}` in serve.json also disables serve's directory-index resolution, so `GET /` rendered a file listing instead of the homepage — a side effect present since July 20 and invisible until the site moved into `site/`. (2) The server was pointed at the repository root, and serve returns `site/index.html` for the URL `/site` without redirecting to `/site/`, so every relative asset resolved one level too high and 404'd. Fixed with one root `serve.json` carrying `public: "site"`, a `/` rewrite, `cleanUrls: false` and `directoryListing: false`, plus `.vscode/settings.json` rooting Live Server at `/site`. `site/serve.json` deleted, and with it the last non-deployable inside the publish directory.
- **LOCAL_SERVE_CLEAN_URL_DROPS_TARGET_QUERY.md** — not an application defect. `npx serve .` (CLAUDE.md's own recommended local test command) 301-redirects `*.html` requests to extensionless clean URLs by default, which drops the `?target=` query string; `loading.html` then falls back to `DEFAULT_TARGET` ("resume") and redirects to the wrong editor once the countdown finishes, which reads like "the countdown isn't working." Netlify has no such redirect, so production was never affected. Fixed by adding `serve.json` (`{"cleanUrls": false}`) at the repo root so local testing matches production. Worth ruling out first if a loading-page flow ever seems to land on the wrong editor again during local testing.

## Operational Knowledge Not Written Down Elsewhere

These cost real time to work out during setup and aren't captured in any other doc — worth reading before touching DNS, Search Console, or Adsterra again.

- **Cloudflare DNS + Netlify domain cutover order matters.** Add the custom domain in Netlify first; if Netlify shows "Netlify DNS propagating" it means it tried to create its own DNS zone — go to the Netlify team's Domains page and delete that DNS zone, then re-add the domain so it shows "Pending DNS verification" instead (external-DNS mode). Only then add the Cloudflare CNAME records.
- **SSL cert sequencing:** keep new DNS records gray-cloud (DNS only) until Netlify's Let's Encrypt certificate shows as issued in Domain management, only then flip to orange-cloud proxied. Proxying before the cert issues can block Netlify's verification. After flipping to proxied, set Cloudflare SSL/TLS to **Full (strict)** — leaving it on "Flexible" causes an infinite redirect loop against Netlify's forced HTTPS.
- **Google Search Console Domain properties want the bare hostname** (`templatebox.win`, no protocol) when creating the property, but want the **full absolute URL** (`https://templatebox.win/sitemap.xml`) when submitting a sitemap — the relative form (`sitemap.xml`) throws "Invalid sitemap address" on a Domain property because the host/protocol is ambiguous.
- **A freshly submitted sitemap shows "Couldn't fetch" instantly**, before Google has attempted any fetch — this is a UI placeholder, not a real failure. Don't chase it via Cloudflare Security Events unless the URL Inspection "Live Test" also fails; if Live Test passes, the sitemap status is cosmetic and will resolve on Google's own schedule (can take 1-2+ days). Forcing a re-check: delete and resubmit, or submit with a cache-busting query string (`sitemap.xml?v=2`) to force a treat-as-new fetch.
- **Cloudflare Security → Events** is the authoritative way to check whether Googlebot (or any specific requester) is being challenged/blocked — filter by path and/or user agent. A `curl` spoofing Googlebot's user-agent from a non-Google IP does NOT reproduce what Cloudflare's bot detection sees, since it checks IP/ASN and reverse DNS, not just the UA header — don't trust that kind of test as conclusive.
- **Adsterra's "Create Ad Unit" dialog only allows one placement per format-and-size per site** — it greys out exact duplicates. A second zone of a size you already have (e.g., a second distinct 300x250 Banner) requires a direct support ticket; be explicit in the ticket that you want a second zone for an *existing* ad slot's separate tracking, not additional ad inventory, or support may push back citing ad-density/CPM concerns. Different Banner sizes are NOT blocked, though: the 728x90, 320x50, and 160x600 blog zones were all created straight from the dashboard on July 18, 2026 with no ticket.
- **Adsterra's "Adult ads" toggle can reset to ON** on ad-unit-creation dialogs even after being turned off elsewhere for the site — recheck it each time before creating a new placement.
- **Ad script page resources always show as "couldn't be loaded" in Google's URL Inspection tool.** This is universal for any ad-monetized site (ad networks block crawler fetches of their own scripts) and is not a problem to fix.
- **Never bind an R2 bucket (or any Cloudflare product) to `templatebox.win` or `www`.** A custom domain binding takes over the entire hostname, so the website disappears — this took the site down on July 30, 2026. Asset hosting belongs on its own subdomain, e.g. `cdn.templatebox.win`. See `R2_CUSTOM_DOMAIN_ON_APEX_TAKES_DOWN_SITE.md`.
- **Verify domain routing by the header pair, never by the status code.** `Server: cloudflare` proves the proxy is in front; `x-nf-request-id` on the *same* response proves the request reached Netlify behind it. Either alone proves nothing — a 404 carrying `x-nf-request-id` is the site's own 404 page and healthy, whereas a Cloudflare-only response means the request never left Cloudflare. A bare 200 is not proof either, because R2 also returns 200 once objects exist.
- **Negative DNS caching outlasts a DNS fix, and local flushes do not reach upstream resolvers.** After the July 30 fix was correct at Cloudflare's authoritative nameservers and at 1.1.1.1/8.8.8.8/9.9.9.9, the local resolver kept returning NXDOMAIN and `Clear-DnsClientCache` did not help. Bypass DNS to test: `curl -D - --resolve templatebox.win:443:<edge-ip> https://templatebox.win/`. Treat a browser still showing an error as unproven, not as evidence the fix failed.
- **Netlify's "Pending DNS verification" plus a proxied record is a known deadlock.** Netlify resolves the hostname and sees Cloudflare's IPs instead of its own load balancer. Add or restore records grey-cloud (DNS only), wait for Netlify to verify and for the Let's Encrypt certificate to list the hostname, and only then switch to Proxied — then confirm SSL/TLS is Full (strict), because Flexible causes an infinite redirect loop against Netlify's forced HTTPS.
- **Two ignorable Cloudflare UI artifacts.** The DNS "Recommendations" panel ("Visitors cannot reach templatebox.win — add an A, AAAA or CNAME record") is cached and persists after the record exists; confirm against the record list instead. The apex-row tooltip about CNAME flattening is Cloudflare explaining that it makes an apex CNAME possible, not a warning.

## Design/Architecture Decisions Made During Build (with reasoning, in case revisited)

- **jsPDF primitives over jspdf-autotable.** The invoice/receipt line-item table, checkbox rows and side-by-side party columns in `js/docs.js` are hand-rolled on `doc.text()`, `doc.rect()` and `doc.line()` rather than adding the autotable plugin. Rationale: it keeps the CDN surface identical to the resume builder's single jsPDF include, and CLAUDE.md mandates the native text API specifically. Do not add autotable to "simplify" the table code without weighing that.
- **No ads on index.html, ever.** Argued out explicitly: index.html is the page Google actually indexes (loading.html is noindex,nofollow), so ad clutter there carries real SEO/trust risk that the isolated loading-page model doesn't. This half of the rule stands.
- **Editors carry one passive banner (revised July 27, 2026).** The original rule was "no ads on the editors either, ever". It was reversed on a dwell-time argument: an editing session lasts minutes where a catalog visit lasts seconds, so one passive unit on an editor plausibly out-earns the interstitial per session at a far lower interruption cost. Four mutually exclusive viewport bands (three-slot 300x250 rail at 93rem and above, single 160x600 rail 84-93rem, 728x90 leaderboard 48-84rem, 320x50 anchor below 48rem), never two bands at once and never none, no active format, iframe-isolated only. Each slot in the stack carries its own zone key -- repeating one key is not three placements. The rail gate is 84rem rather than 75rem because below that the page is capped by the viewport instead of its own max-width, so the rail stops using spare margin and starts eating the editing panes — at 1200px it cost each pane 68px against the pre-rail layout. The isolation is what keeps "nothing leaves your device" honest, so **Native Banner and any other page-context format is prohibited on editors**. Full reasoning and rejected alternatives: `docs/implementation/EDITOR_PAGE_AD_PLACEMENT.md`. Four documents were updated to match (`PRD.md`, `CLAUDE.md`, `site/privacy.html`, `site/terms.html`, `site/about.html`) — if this is ever reversed again, all of them need revisiting.
- **Reused Adsterra banner keys across both slots is fine** functionally; a second zone was obtained purely for separated reporting, not because sharing was broken.
- **CSP is intentionally not in `netlify.toml` yet** — Adsterra's ad domains rotate/vary enough that a hand-written allowlist would likely break ads; revisit once ad domains are observed to be stable.
- **jsPDF over html2pdf.js** is now the mandated PDF engine project-wide (CLAUDE.md and PRD.md both updated) — do not reintroduce html2pdf.js.
- **Loading-page countdown resilience (July 21, 2026).** The countdown text (`10`) is static markup in `loading.html`, so if `js/app.js` ever fails to load or throws before scheduling its timer, the page freezes at 10 forever with no redirect — indistinguishable from "the countdown isn't working," and distinct from the already-solved stall-at-zero defect in LOADING_REDIRECT_STALL_FIX.md (that one starts the timer but loses the redirect race; this one never starts the timer at all). Two changes close the gap: (1) the `DOMContentLoaded` boot handler in `js/app.js` now runs `initCatalog`/`initLoadingPage`/`initEditorTabs` each in its own `try/catch` instead of as unguarded sequential calls, so a throw in one can't block the others; (2) `loading.html` carries a small inline, dependency-free fallback script (after the `js/app.js` include) that waits 1.5s, checks a `window.__tbLoadingActive` flag `initLoadingPage()` sets on success, and if unset runs its own identical countdown/redirect against its own copy of the route whitelist. Verified with Playwright: normal path completes in 10s as before; with `js/app.js` blocked, the fallback completes in ~12s and lands on the correct editor; a 10-case fuzz of the fallback's whitelist (valid/missing/unknown targets plus six hostile payloads: absolute URL, protocol-relative, path traversal, `__proto__`, `constructor`) all resolved to the correct or default editor with nothing escaping to an external host. Full write-up: `docs/implementation/MOCKUP_GENERATOR_IMPLEMENTATION.md`.
- **Mockup generator (July 20, 2026): flat-vector Canvas products, no image assets.** Rather than photographic mockup templates (which would need licensed/hosted product photos), all four products are drawn as flat vector illustrations directly in `js/mockup.js`, matching the site's "no gradients, no drop shadows" theme and keeping the tool's payload at zero images, consistent with the poster editor's approach. The mug handle's arc deliberately oversweeps past 90 degrees on each side so it tucks behind the body edge instead of floating disconnected — worth knowing before adjusting that shape. The "Add to My Mockups" tray is the closest honest stand-in for "add to products in one click" a database-free tool can offer (there is no real product catalog to attach to); it lives in memory only, not localStorage, for the same image-quota reason `poster.js` never persists the uploaded photo. Full write-up: `docs/implementation/MOCKUP_GENERATOR_IMPLEMENTATION.md`.
- **Business document builder (July 21, 2026): one editor, six catalog cards.** Rather than six near-duplicate pages, `docs.html` drives all six documents from one form and one state object; fieldsets carry `data-for` lists of the document keys they belong to and labels are re-worded from a per-type `labels` map, so the same input reads "Received From (Tenant)" on a rent receipt and "Employee Name" on a warning notice. Hidden fields are still collected into state, deliberately, so switching document types never loses typed data. Three layout families (`receipt`, `itemized`, `notice`) each have one preview renderer and one jsPDF writer. Two things worth knowing before touching it: (1) `CURRENCIES` carries two symbols per entry because jsPDF's built-in fonts are WinAnsi-encoded and cannot draw the rupee/naira/cedi glyphs — those use an ASCII prefix in the PDF only, while dollar/euro/pound/yen are inside cp1252 and print as-is; (2) the PDF table, checkbox and two-column-party primitives are hand-rolled on top of `doc.text()`/`doc.rect()`/`doc.line()` rather than pulling in jspdf-autotable, keeping the CDN surface identical to the resume builder's. The "Blank printable form" toggle is what makes the printable-form cards distinct: empty optional fields render as ruled lines instead of being omitted. Full write-up: `docs/implementation/BUSINESS_DOCUMENT_BUILDER_IMPLEMENTATION.md`.
- **Grid children need `min-width: 0` (July 21, 2026).** `.editor-pane` / `.preview-pane` are CSS grid children and so default to `min-width: auto`, meaning they refuse to shrink below their content's minimum width. The invoice line-item table (four columns, irreducible below roughly 272px) therefore pushed its own pane past its grid track and scrolled the entire page sideways at a 320px viewport — a PRD violation that looked like a table bug but was a grid-sizing default. Fixed with `min-width: 0` on both panes plus an `overflow-x: auto` wrapper on the table, the same containment approach already used on `.ad-slot`. Worth checking first if any editor ever overflows horizontally on mobile.
- **Footer social icons (July 25, 2026): inline SVG, no external assets.** Every public page's `site-footer` carries a `.footer-social` row (between the `.footer-links` nav and the tagline) linking to X (`https://x.com/Templatebox26`), Facebook (`https://www.facebook.com/profile.php?id=61592027191178`), TikTok (`https://www.tiktok.com/@templatebox26`), and Instagram (`https://www.instagram.com/templatebox26/`). Icons are inline SVG paths using `currentColor` (muted, darkening on hover/focus), 2.75rem tap targets matching `.footer-links a`, `target="_blank" rel="noopener noreferrer"`, `aria-label` on each anchor. The block is identical across all nine public pages (admin.html deliberately excluded as a private tool); if the handles ever change, update all nine. Print styles already hide `.site-footer`, so PDFs/prints are unaffected. Verified in-browser at 411px and 320px: no horizontal overflow, no console errors.
- **UI/UX and SEO audit implementation (July 26, 2026).** Both audits are written up in full at `docs/project/UI_UX_AUDIT.md` and `docs/project/SEO_AUDIT.md`, with per-finding status. The decisions most likely to be second-guessed later:
  - **Catalog CTAs are anchors, not buttons.** Every launch control is now `<a href="<editor>.html" data-target="...">`, intercepted by `bindLaunchControls()` in `js/app.js`, which calls `preventDefault()` and routes through `loading.html` exactly as before. Nothing about the monetized flow changed for a human visitor. The reason for the change is that Googlebot does not click buttons, so all four editor pages previously had **zero** inbound internal links from anywhere on the site and were discoverable only via the sitemap. Modified clicks (ctrl/cmd/shift/middle) are deliberately passed through to the browser. Do not convert these back to buttons.
  - **Landing pages exist because one URL cannot rank for six intents.** `docs.html` serves six document types under one title; Google ranks URLs, not features. Nine static landing pages now each own one intent and convert into the editor with the right `data-doc` preset. They were generated once from a template and are now plain static files: edit them directly, there is no generator to re-run.
  - **Loading page copy was dishonest and is now not.** It claimed to be "loading editing canvas, typography fonts, and template assets", which describes work that does not happen (the editors are static pages). That is a dark pattern, it is visible in Clarity session replay, and it bought nothing. The interval, ad count, zone keys and watchdog are all unchanged; only the wording, a progress bar, and naming the chosen template were added.
  - **Blog posts are static files now; `post.html` is a noindex fallback.** See the blog entry below for the full reasoning.
  - **No design-system tooling was introduced.** At one stylesheet, nine pages and one contributor, a synced design-system project would be a second artifact to reconcile by hand while the real work still lands in `css/style.css`. A token layer (`--space-*`, `--motion-*`, `--color-brand`) delivers the substance inside the existing no-build constraint. Revisit past roughly ten tools or a second contributor.
  - **`--accent` and `--color-brand` are deliberately separate.** `--accent` is the per-document colour the resume swatch row overwrites; `--color-brand` is the site's interactive accent. Before this pass `--accent` was `#1A1A1A`, identical to `--color-text`, so outside the resume editor the site had no accent colour at all.
- **Blog moved to static per-post pages (July 26, 2026).** `post.html` resolved every post's title, description, canonical and BlogPosting schema at runtime from `js/blog.js`. Google renders JavaScript but only on a deferred second pass, and **social crawlers never execute JavaScript at all**, so every post shared to Facebook, X, LinkedIn or WhatsApp previewed as the generic "Article | TemplateBox Blog" with no description or image. `admin.html` now has a **Download Post Pages** action emitting `blog/<slug>.html` per post with real metadata in the markup; it builds the body by running the post through the existing `TBBlog.renderBlocks` and serializing the result, so there is still exactly one block renderer in the project and the static output cannot drift. `netlify.toml` 301s `post.html?slug=` to the static file (a redirect rather than a noindex, so already-indexed query URLs pass their signal on instead of losing it), and the admin draft preview moved to `post.html?draft=<slug>&preview=1` so the redirect cannot bounce an unexported draft. **When publishing: export blog-data.js, export the post pages into `blog/`, and add the new URL to `sitemap.xml`.**
- **Deployables moved into `site/`; the publish directory is now the web root (July 27, 2026).** Carried out on request after being deferred earlier the same day. The move is cheap precisely because the publish directory becomes the web root: `site/index.html` is served at `/index.html`, so no canonical, `og:url`, sitemap entry, inbound link or relative asset path needed rewriting. What it buys is that documentation and instruction files cannot be published by accident — a structural guarantee instead of a list of 404 rules to extend every time a note is added. Ten of the eleven rules were deleted; `/serve.json` keeps one because `serve` reads that config from the directory it serves, so it has to ship inside `site/`. Pages stay flat within `site/`, so the reason a `pages/` subfolder was rejected still holds: directory layout is URL layout, and nesting pages would rename every public URL for tidiness alone. Local testing is now `npx serve site`; serving the repository root would break every relative path. Full write-up: `docs/implementation/SITE_PUBLISH_DIRECTORY_MIGRATION.md`.
- **Footer restructured into five columns, applied from one script (July 27, 2026).** "Creative Tools" mixed three landing pages with two of the four editors, which is why `docs.html` and `poster.html` looked arbitrarily omitted. Now: Receipts and Invoices, Resumes and Creative, Editors (all four), Learn, Company. `.footer-cols` is `repeat(auto-fit, minmax(11rem, 1fr))`, so the fifth column needed no CSS. Two drift cases were normalized at the same time: `privacy.html` alone used a `<details>` accordion footer that no CSS rule styles, and the nine landing pages indented the opening `<footer>` tag at column 0 rather than four spaces. All 22 copies plus the `FOOTER` constant in `js/admin.js` were written by one script and verified byte-identical — hand-editing 22 copies is what caused every footer defect so far, so do it that way again.
- **Footer link columns and the guides page are separate systems with zero overlap, by construction (July 27, 2026).** Asked why the footer's pages do not appear on the guides page. The footer is hand-written HTML whose two content columns list the nine landing pages; `blog.html` renders only from `window.TB_BLOG_POSTS` in `js/blog-data.js`, currently one post. No code path joins them, and `blog.html` carries no article markup at all — the list is built entirely in JS behind a `<noscript>` line. Related and more consequential: the **only crawlable link to a blog post was `sitemap.xml`**, because the homepage guides strip (`js/app.js`) and the blog cards (`js/blog.js`) both create their anchors in JavaScript — the same orphaning defect the July 26 pass fixed for the editor pages by converting buttons to anchors. Fixed later the same day with the static guides archive on `blog.html`; the homepage strip is deliberately still a JavaScript render, because it is a "latest three" widget and no longer the discovery path. The footer columns and the archive list remain separate hand-maintained things, which is correct: one is site navigation, the other is generated from post data.
- **Landing pages carry one passive banner, deliberately not in the hero (July 27, 2026).** Asked why the template landing pages had no ads when the hero has visible empty space. That space is a grid artifact, not a slot: the 4:5 preview column is always taller than the headline/CTA column, and `align-items: start` piled the difference under the CTA (now `center`). The hero is also the worst possible placement, because these pages exist to send clicks into `loading.html`, where a Popunder, two 300x250s and the Social Bar run across a ten-second dwell — worth far more than one banner impression from a visitor about to leave. One 300x250 now sits between the body copy and the FAQ, above both the closing CTA band and related templates. Passive format only; Popunder and Social Bar stay off every indexable page. Full reasoning, including the placements rejected and when a second unit would be justified: `docs/implementation/LANDING_PAGE_AD_PLACEMENT.md`.
- **Ad placement extracted to `js/ads.js` (July 27, 2026).** The registry lived inside the 790-line `js/blog.js`; landing pages were the third page family to need it. Loading a content library on nine marketing pages to fill one banner is waste, and a second copy of the zone table is the drift that caused two defects already, so the concern moved to a 187-line dependency-free module (`TBAds`). Auto-mounting is opt-in via `data-ads-static` on `<main>`, which is what stops a renderer-driven page double-counting impressions. Consequence worth knowing: the generated post pages no longer load `js/blog.js` or `js/blog-data.js` at all — neither was read there, and the post database grows with every published post.
- **Blog (July 18, 2026): serverless admin-panel model.** No database means the blog "publishes" by exporting a static `js/blog-data.js` from `admin.html` (drafts live in that browser's localStorage under `tb_admin_posts`) and deploying it. Post bodies are typed blocks rendered createElement/textContent-only — never HTML strings. Blog pages are a monetized surface (banners only, passive formats); the no-ads rule still holds for index.html and the editors, and Popunder/Social Bar are deliberately kept off blog pages because they are indexable content. Ad placements live in the `AD_ZONES` registry in `js/blog.js`: a placement with an empty key renders nothing (zero layout shift), so 728x90/320x50/160x600 activate by pasting keys once Adsterra provisions the zones. Full write-up: `docs/implementation/BLOG_SYSTEM_IMPLEMENTATION.md`.

- **Photographic mockup templates (July 30, 2026): registry-driven Sandwich Method inside the existing editor, not a separate gallery app.** The research spec (MOCKUP_CONTEXT.MD at the repo root) described a Mockey/Placeit-style gallery page with an editor modal; that shape was deliberately not built because index.html already is the gallery and a same-page modal would bypass the mandatory loading.html ad interstitial. Each photographic template is a catalog card (`data-target="mockup" data-doc="<id>"`) using the same preset hand-off docs.html uses. Compositing order is declared per template because the purchased asset style has a fully transparent print window in the base: mode "window" draws design first (over a white paper backing), then the base whose antialiased window edge masks it, then the overlay; mode "surface" is the classic base-first order for opaque assets. **The overlay's blend mode is also per-template (`overlayBlend`) and it is the single most consequential field**: this asset's overlay is a baked luminance map (alpha 193 over a near-white body inside the window), so at the canvas default `source-over` it painted over the artwork and desaturated it completely — a design colour of (196,138,74) sampled as (234,219,204). At `multiply` it samples (190,134,72) and the window-light and pampas shadows fall across the design convincingly. Canvas silently ignores an unrecognized composite operation and leaves `source-over`, so the value is whitelisted in code; a typo would otherwise reintroduce the washout with no error anywhere. See `docs/error-fixes/PHOTO_MOCKUP_OVERLAY_WASHES_OUT_DESIGN.md`, which also records how to pick the mode from an asset's appearance. The warpZone is stored as four corners so angled frames slot in later: rectangular zones use the existing contain/drag/scale 2D path, non-rectangular zones will lazy-load the vendored glfx.js and map corner-to-corner (that path is dormant and unverified until a real angled asset exists — the cdnjs glfx URL in the research notes is a 404, which is why the library is vendored from jsdelivr instead of CDN-linked). Coordinates for wood-a4 came from an alpha-channel scan of the base (window: x 655-1461, y 224-1583 in 2000x2000); future templates use tools/mockup-admin.html. Asset names must be URL-safe — the supplied thumbnail folders ("Product Mockups/Posters,frames,canvas, billboards") contained spaces and commas and were renamed to kebab-case before anything could reference them. Full write-up: `docs/implementation/PHOTO_MOCKUP_TEMPLATES_IMPLEMENTATION.md`.

## Extending TemplateBox: Adding a New Template/Editor

Pattern demonstrated by resume.html/docs.html/poster.html/mockup.html, to follow for a fifth tool:

1. Add a card to the `.catalog-grid` in `index.html`. The CTA must be an **anchor** — `<a class="btn btn-block card-link" href="yourpage.html" data-target="yourkey">` — not a button, or the new editor page will have no crawlable inbound link (see the July 26 decision log). Give the card a `data-category` matching an existing or new filter pill, and a filled `.mock-doc` miniature rather than an empty preview. If the new editor serves several cards, also give each card a `data-doc="variantkey"` and consume it with `TB.takePreset()` (see the docs.html pattern above).
2. Add `yourkey: "yourpage.html"` to `EDITOR_ROUTES` in `js/app.js`, to the `EDITORS` registry beside it (label plus the localStorage key the editor writes, which powers the continue strip and the loading page's template name), **and** to the mirrored inline `ROUTES` table in `loading.html` — this is what keeps the loading-page redirect safe from tampering, on both the normal and the fallback path.
3. Build `yourpage.html` + `js/yourpage.js` following the resume/poster split-pane pattern: `.editor-layout` / `.editor-pane` / `.preview-pane` / `.mobile-tabs` CSS classes are already themed and responsive; `TB.sanitize`, `TB.desanitize`, `TB.storageGet`, `TB.storageSet` from `js/app.js` are the shared utilities to reuse for localStorage binding and XSS-safe rendering. Also include the shared editor furniture: `.breadcrumb`, `.editor-head` with `<p class="save-state" id="save-state">`, the export control inside `.preview-actions`, and a `.related-tools` block. Call `TB.markSaved()` after every `TB.storageSet` so the autosave indicator reflects reality.
4. No ad work needed — the new tool automatically routes through the existing monetized `loading.html` flow.
5. Add SEO meta tags, canonical URL, Twitter Card tags, and `SoftwareApplication` + `BreadcrumbList` + `Organization` JSON-LD following the pattern in resume.html/docs.html. Add the new page to `sitemap.xml` with a `lastmod`, and add it to the appropriate footer column — a landing page goes in "Receipts and Invoices" or "Resumes and Creative", an editor in "Editors". The footer is byte-identical across all 22 pages plus the `FOOTER` constant in `js/admin.js`, so change it by generating the block once from a script and writing it to every copy, not by hand-editing 22 files (see the July 27 decision entry).
6. If the new tool serves a distinct search intent, give it a landing page too, following the shape of `rent-receipt-template.html`: own title/H1/canonical, real body content, `FAQPage` schema, and a CTA into the editor with the right preset.
