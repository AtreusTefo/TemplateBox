Blog Admin

Write and manage blog posts locally, then export the data file and deploy it. Nothing here touches a server: drafts live in this browser's storage until you publish the exported js/blog-data.js through Git or Netlify.

Publish

How publishing works
  1. Save your posts below. They are stored only in this browser.
  2. Click Download js/blog-data.js and replace the existing file at js/blog-data.js in the project. This drives the blog index and the card lists.
  3. Click Download Post Pages and put every downloaded file into the project's blog/ folder. One static page per post.
  4. Click Copy Guides Archive and paste it over the <ul> inside <nav class="guide-archive"> in blog.html. This is the only link to a post in the served markup, so a post left out of it is invisible to anything that does not run JavaScript.
  5. Add any new post URL to sitemap.xml as /blog/<slug>.html.
  6. Commit and push to main (Netlify auto-deploys), or drag the site folder into Netlify.
  7. Visitors now see the updated posts on the live blog.
Why post pages are exported as separate files

post.html resolves a post's title, description and structured data at runtime with JavaScript. Google renders JavaScript but only on a deferred second pass, and social crawlers (Facebook, X, LinkedIn, WhatsApp) never run it at all, so a shared link previewed as a generic "Article" with no description.

The exported files carry the real metadata in the served markup, so search engines and social previews get it immediately. post.html still works as a fallback route for any existing link.

Catalog Thumbnails

How catalog thumbnails are published
  1. Pick a catalog item below, or choose "Add a new catalog item" and describe it.
  2. Upload the default thumbnail. This is what the card shows at rest, and it is required.
  3. Optionally upload a hover thumbnail. Leave it empty and the card simply has no hover state, which is a valid card.
  4. Save. The item joins the list above, stored in this browser only.
  5. Click Publish on the item, or Publish All. The images are written into the right folder and index.html is edited for you. Steps 6 and 7 are then already done.
  6. Without a connected folder: click Download and put the files in the folder shown on the row. Both are already named to the project convention.
  7. Without a connected folder: click Copy Markup and paste it into index.html, over the item's existing <div class="card-preview"> block for an existing card, or as a new <article> inside <div class="catalog-grid"> for a new one.
  8. Review the change with git diff, then commit and push to main (Netlify auto-deploys), or drag the site folder into Netlify. Deploying is always yours to do: no page can push to your repository on your behalf.
What Publish changes, and what it will not touch

Publish writes the image files into the folder named on the row, removes any older file for the same card left behind under a different extension, and then edits index.html.

That edit is a byte-level splice of one element, not a rewrite of the file. Every other byte stays identical, so git diff shows only the card you changed.

Before the edited file is written it is parsed and checked: the markup must parse, the card count must be what was expected, every other card's category, link, variant and title must be unchanged, and the new image paths must actually appear. If any check fails, index.html is left exactly as it was and the panel says so.

Images are written before the markup on purpose. If a publish fails midway, the worst case is an image file nothing references yet, which is harmless. The other order would leave the homepage pointing at a file that was never written.

Only the site folder is reachable, and only after you pick it. The panel refuses any folder without an index.html and an assets directory, so pointing it at the wrong place fails immediately rather than scattering files.

Why images are downloaded instead of saved

TemplateBox has no server and no build step, so a browser page cannot write into the project's assets/ folder. Thumbnails are held here as data URIs in this browser's storage purely so the form survives a refresh; the published copies are the real files you place in the repository, exactly as post pages work.

That is also why the compression budget is tight. Storage is a few megabytes in total and is shared with the blog workspace, and the thumbnails already shipping are 46 to 83 KB each.

What compression does to your image

Uploads are resized to a 1000px long edge and re-encoded until they fit in 60 KB, entirely in this browser. Nothing is uploaded anywhere.

This is lossy, and it has to be: that is what takes a multi-megabyte photograph down to tens of kilobytes. What it protects is how the image looks where it is actually used. A catalog card renders roughly 240px wide, so a 1000px thumbnail still carries four times the detail the card can show, and the compression is spent on detail no visitor sees.

The encoder keeps the highest quality that fits rather than a fixed setting, and prefers WebP where the browser can write it, because WebP reaches the same appearance in roughly a third fewer bytes than JPEG. It only gives up pixels when quality alone cannot reach the budget. An image that already fits is kept exactly as uploaded and never re-encoded.

For the sharpest result, upload the largest clean copy you have and let this do the resizing. Compressing it yourself first and then uploading means the image is compressed twice, which is what actually produces visible artefacts.
